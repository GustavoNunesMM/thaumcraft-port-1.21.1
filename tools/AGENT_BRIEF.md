# Brief for agents porting Thaumcraft 6 (1.12.2) to NeoForge 1.21.1

Repo layout (paths relative to the repo root):
- `mod/` — the NeoForge 1.21.1 port (Java 21, ModDevGradle, Parchment). Build from `mod/`: `./gradlew build`; server tests: `./gradlew runGameTestServer` (must end with "All N required tests passed").
- `reference/thaumcraft/` — the 1.12.2 source, decompiled with readable names. This is the spec: port behaviour faithfully.
- `decompiled/assets/thaumcraft/` — original assets (blockstates, models incl. OBJ, textures). All textures are already copied to `mod/src/main/resources/assets/thaumcraft/textures/`.
- `tools/gen_marco*.py` — generators for JSON resources. Look at `tools/gen_marco7.py` and `tools/gen_marco8.py` as the model for yours.
- `tools/convert_recipes.py` already converted ALL arcane/crucible/infusion recipes into `mod/src/main/resources/data/thaumcraft/recipe/`, each guarded by `neoforge:item_exists` conditions: they switch on by themselves once you register items with the expected ids. Research entries (JSON) are already converted too. Check the recipe JSONs to learn the registry ids expected for your items (`grep -rho '"thaumcraft:[a-z0-9_]*"' mod/src/main/resources/data/thaumcraft/recipe | sort -u`).
- Lang: `assets/thaumcraft/lang/en_us.json` and `pt_br.json` already contain the 1.12 keys (`item.x.name`, `tile.x.name`) with full pt_br translations. New 1.21 keys (`item.thaumcraft.<id>`, `block.thaumcraft.<id>`) must be added by YOUR gen script copying from the old keys (both languages, Brazilian Portuguese with accents). Never leave a key untranslated in pt_br.

Conventions already in place (read these files first):
- `common/blocks/DeviceBlock.java` (facing/enabled base, like BlockTCDevice), `common/blocks/TCBlockEntity.java` (readSync/writeSync/readExtra/writeExtra + `sync()`, like TileThaumcraft).
- Registries: `common/registers/Mod*.java`. Aspects: `thaumcraft.api.aspects.*`, `AspectHelper`, `common/aspects/AspectManager`. Aura: `common/world/aura/AuraHandler` (getVis/drainVis/addFlux...). Research: `common/research/ResearchManager` (knowsResearch, completeResearch, addWarp...).
- Essentia: `api/aspects/IEssentiaTransport`, `IAspectSource`, `common/lib/EssentiaHandler`. Infusion: `api/crafting/InfusionRecipe`, `common/blocks/infusion/*`, `common/lib/enchantment/EnumInfusionEnchantment`.
- Casters: `api/casters/*` (focus API, already ported), `common/items/casters/CasterItem.java`, `CasterManager.java`.
- Data components: `common/registers/ModDataComponents.java` (ESSENTIA, ASPECT_FILTER, INFUSION_ENCHANTMENTS, WARP, FOCUS_PACKAGE, CASTER_FOCUS, PICKED_BLOCK, CASTER_AREA).
- Client FX: `client/fx/FXGeneric.java`, `FXDispatcher.java`, `EssentiaFX.java`, `InfusionFX.java`. Renderers: `client/renderers/RenderUtil.java` (glRotatef helper `rot`, `pointUpTo`, `quadCentered`) and `EssentiaRenderers.java` / `InfusionRenderers.java` show how 1.12 ModelRenderer models become LayerDefinitions with the GL calls translated one to one.
- Client registration pattern: a `@EventBusSubscriber(modid = Thaumcraft.MODID, value = Dist.CLIENT, bus = EventBusSubscriber.Bus.MOD)` class per milestone (see `client/EssentiaClient.java`, `client/InfusionClient.java`).
- Gametests: `gametest/*GameTests.java`, templates `empty` (small) and `trees` (33x40x33 room).
- Curios 9.5.1 (required dependency, replaces Baubles) is on the classpath: `top.theillusivec4.curios.api.*`. Slot types: `necklace` (amulet), `ring`, `belt`, `charm`, `head`, `body`... register item tags `curios:<slot>` via data `data/curios/tags/item/<slot>.json`, plus enable slots for players with `data/<modid>/curios/entities/*.json` if needed.

RULES to avoid merge conflicts (several agents work in parallel on other milestones):
1. Put your Java code in your own packages/files. Do NOT reorganize or reformat existing files.
2. Registries: do NOT add entries to `ModBlocks`, `ModItems`, `ModBlockEntities`, `ModEntities`, `ModMenus` directly. Create your own holder class (e.g. `common/registers/ModGolems.java`) whose static fields register into the EXISTING DeferredRegisters (`ModBlocks.BLOCKS.registerBlock(...)`, `ModItems.ITEMS.registerItem(...)`, `ModBlockEntities.BLOCK_ENTITIES.register(...)`, etc.), with a `public static void init() {}` that you call with ONE line added to the `Thaumcraft` constructor before the `register(modBus)` calls. Register your BlockItems yourself in that class. New registry kinds (entities, mob effects, menus...) may need their own DeferredRegister in your class, registered with one line in `Thaumcraft`.
3. Network payloads: create your own class with `public static void register(PayloadRegistrar r)` and call it with ONE line from `ModNetwork.register`. Client handlers may call your client classes directly from the lambda (it only runs on the client).
4. Resources: generated by YOUR script `tools/gen_<milestone>.py` (models, blockstates, loot tables, tags, lang keys, extra recipes). Never hand-edit shared JSON (lang files, `data/minecraft/tags/...`, aspect files); always merge-update them from your script (load, add, write), so the script can be re-run after merging. Do not run the older gen_marco2.py.
5. Don't edit `README.md`. Don't touch other milestones' features.
6. Things from milestones not ported yet: stub them minimally and say so in a comment, and list them in your final report.
7. When done: `./gradlew build` and `./gradlew runGameTestServer` must pass (add gametests for your core mechanics). Then `git add -A && git commit` in your worktree with a message ending with the line `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
8. Final report (short): branch name, what was ported, what was stubbed/left out, new registry ids, the gen script name, test results.
